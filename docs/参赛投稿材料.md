## 3. 社媒正文（公众号 / 小红书通用，按需删减）

**标题备选**

- 便签打开慢了半年，我让 Hy4 把它从头"体检"了一遍
- 132ms / 361ms：一次用 Hy4 做的真实启动性能排障
- 不是写 Demo：用 Hy4 给正在用的软件排障、加功能、补工程化

**正文**

```
#WorkBuddy #Hy4

手头这套便签工具我自己天天在用，但一直有两个毛病：服务启动慢，桌面端登录之后窗口偶尔会直接消失。趁 Hy4 限免，把它当成一件真活交给了 WorkBuddy，而不是问一句"怎么优化启动速度"就完事。

【第一步｜先量，再猜】
Hy4 没有上来就改代码，而是先加了启动分段计时，把耗时摊开：import_app 约 3.2s、logging、database、scheduler。/health 能直接返回各阶段毫秒数，于是"感觉慢"变成了"database 阶段 361ms，其中约 3.2s 是 FastAPI/Pydantic 的导入固定成本，与业务无关"。这个结论很重要——它避免了我去优化根本优化不动的部分。

【第二步｜逐项 A/B】
- seed.py 每次启动全量 SELECT + DELETE + INSERT ≈45 次查库 → 加内容指纹闸门，稳态只做 3 次校验查询
- 权限集合未变化仍重写关联表 → 改成差集写入
- DEBUG=True 连带 echo 全部 SQL → DEBUG 与 echo_sql 解耦
- httpx 等重依赖延迟到首次使用才导入
- 老库接入 Alembic 后，稳态仍不 import alembic（用标准库 ast 求 head），否则 database 阶段会从约 120ms 涨到约 900ms

实测 8 轮交替 A/B 取样中位数：database 361ms → 132ms，约 2.7×。总启动在 3.6—5.3s 波动，差值落在噪声里，我在项目文档里如实标注"不作为优化结论"——没有把总时间硬吹成提速。

【第三步｜顺手把办公功能补上】
会议纪要 / 今日待办 / 周报 / 需求速记一键插入，状态栏实时显示字数与待办完成进度，单张便签导出 .md，整机备份 JSON 导入导出（字段白名单、坏数据跳过）。桌面端"恢复便签"从一次全开改成最多 8 窗 + 双击按需打开，300KB 的 highlight.js 改成 window.load 后再加载。

【第四步｜一个真实的坑】
登录后窗口消失，日志里只有一行：signal only works in main thread of the main interpreter。Hy4 顺着堆栈定位到 pywebview/WinForms：js_api 回调线程里创建首个窗口会触发 signal.signal(SIGINT)，而登录窗已先 destroy，异常被吞 → 零窗口 → 主循环退出。改法是主线程预建隐藏便签桌、先 activate 成功再销毁登录窗。这类问题最值钱的地方不是补丁，而是它要求模型同时读懂日志、线程模型和窗口生命周期。

【第五步｜工程化收尾】
开放注册不再绑定 admin、令牌吊销与 refresh 一次性轮换、工作单元事务、滑窗限流、密钥分离、CI + Alembic 基线迁移。最终：ruff 0 错误，后端 78 passed，桌面逻辑 11 passed，alembic check 干净，正式库数据 users=2 / notes=1 / roles=4 未变。

【真实感受】
Hy4 让我比较满意的是长链条任务不容易断线：从加计时、跑 A/B、看堆栈、改多前端代码到补测试和迁移，上下文能一直兜住。也有需要我拍板的地方——它一度建议把数据库初始化和调度器并行，实测反而因为抢 SQLite 首次连接更慢，改回串行；接入迁移层让启动变慢，也是一起找到的快速路径解法。所以我的用法是：让它把可复现的数字和证据摆出来，结论由我复核。这比"一键生成"更像是真的在协作。

项目本身是 9 月就在用的老工具，这一轮是活动期内用 Hy4 做的诊断与增强，过程、数据和踩坑都记在上面了。
```

> 评分里「点赞 + 收藏」占 70 分，建议首图做「361ms → 132ms」前后对比，标题带具体数字；正文比纯技术堆砌更容易被收藏。
